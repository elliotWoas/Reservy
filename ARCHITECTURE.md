# Architecture Documentation — Reservy

Reservy is a production-grade, multi-tenant online service booking SaaS platform engineered with **Clean Architecture & Domain-Oriented Modular Monolith** principles.

---

## 1. Core Architecture Principles

```text
┌─────────────────────────────────────────────────────────────┐
│                      Presentation Layer                     │
│    Next.js 14+ (App Router, Tailwind CSS, RTL, Jalali)      │
│    - Public Storefront (/[slug]) & 6-step Booking Wizard    │
│    - Business Dashboard (/dashboard) & Calendar             │
│    - Platform Super Admin (/admin)                          │
└──────────────────────────────┬──────────────────────────────┘
                               │ REST / JSON
┌──────────────────────────────▼──────────────────────────────┐
│                    API & Core Modules Layer                 │
│                 (apps/api - Modular Monolith)               │
│  ┌──────────────┐ ┌──────────────┐ ┌──────────────────────┐ │
│  │Tenancy & IAM │ │   Catalog    │ │ Availability Engine  │ │
│  └──────────────┘ └──────────────┘ └──────────────────────┘ │
│  ┌──────────────┐ ┌──────────────┐ ┌──────────────────────┐ │
│  │   Booking    │ │ Card Payment │ │   CRM & Reporting    │ │

│                    Domain & Data Layer                      │
│   - @reservy/domain (Pure state machines & slot algorithms) │
│   - @reservy/database (PostgreSQL + Prisma ORM)             │

```

### Module Boundaries & Independence
Modules communicate via strictly defined interfaces and service contracts. Core business domain rules do not depend on HTTP frameworks, specific UI frameworks, database ORMs, or third-party SMS/storage vendors.

Modules include:
1. **Tenancy & IAM**: Multi-tenant isolation, organization membership, and role/permission matrix.
2. **Catalog & Resources**: Generic service catalog, staff members, service assignments, and resources (rooms/equipment).
3. **Availability Engine**: Slot generation algorithms based on working shifts, breaks, buffer times, and blocked periods.
4. **Booking**: Concurrency-safe booking engine, snapshot records, and state machine transitions.
5. **Payment & Receipt Hub**: Card-to-Card payment workflow, receipt validation, and verification audit trail.
6. **CRM & Reporting**: Customer histories, visit stats, and aggregated financial metrics.
7. **Platform Super Admin**: Platform-level oversight and tenant activation/suspension.

## 2. Multi-Tenancy & Tenant Isolation

Tenant isolation is treated as a security boundary:

```text
Tenant (Top-level company/group)
 └── Organization (Independent business unit / slug)
      ├── Location (Branches)
      ├── CardAccount (Bank payment destination)
      ├── Services & Staff
      ├── Customers (Organization-scoped CRM)
      └── Bookings & Payments
```

### Isolation Enforcement
- **Backend Tenant Context**: Every authenticated request resolves `organizationId` from JWT membership and validated `X-Organization-Id` header.
- **Database Query Scoping**: All queries and mutations (`where: { organizationId }`) are scoped to the authenticated organization.
- **Role & Permission Guard**: `requirePermission(Permission.PAYMENT_VERIFY)` checks role-based capabilities before executing controller actions.

## 3. Availability Engine & Timezone Strategy

### Timezone & Storage Rule
- **Canonical Datetimes**: Stored in standard UTC (`timestamptz`) in PostgreSQL.
- **Timezone Conversion**: Evaluated using the organization's timezone (`Asia/Tehran` by default).
- **Jalali Calendar**: Gregorian to Solar Hijri conversion is purely a presentation-layer concern.

### Slot Generation Engine
```text
Available Slots = (Daily Shifts - Breaks - Blocked Periods - Existing Active Bookings)
                  ÷ (Service Duration + Buffer Before + Buffer After)
```

Discrete non-overlapping slots are generated by the backend and returned chronologically.

## 4. Double-Booking & Concurrency Prevention

To eliminate race conditions and double bookings when multiple customers attempt to book the same provider simultaneously:

1. **Transactional Boundary**: All booking operations execute inside an atomic database transaction (`prisma.$transaction`).
2. **Overlapping Collision Query**:
   ```sql
   SELECT id FROM bookings
   WHERE organization_id = :orgId
     AND staff_id = :staffId
     AND start_at < :searchEnd
     AND end_at > :searchStart
     AND status NOT IN ('CANCELLED', 'REJECTED')
     AND deleted_at IS NULL
   ```
3. **Buffer Consideration**: `searchStart = startAt - bufferBefore` and `searchEnd = endAt + bufferAfter`.
4. **Immediate Abort**: If a conflicting record is found, the transaction is rolled back and `DomainError(BOOKING_SLOT_UNAVAILABLE)` is returned with HTTP 409.

## 5. Card-to-Card Payment Workflow

```text
Customer creates booking (Status: PENDING_PAYMENT)
   │
   ▼
System displays Organization Bank Card (Card Number, Holder Name, Bank)
   │
   ▼
Customer transfers money & uploads Receipt Image/PDF
   │
   ▼
Server validates magic bytes MIME type (JPG, PNG, WEBP, PDF) & saves UUID file
   │
   ▼
Payment status -> PROOF_SUBMITTED | Booking status -> PAYMENT_SUBMITTED
   │
   ▼
Business Admin reviews receipt in Dashboard
   ├── Approved -> Payment: VERIFIED, Booking: CONFIRMED (SMS sent)
   └── Rejected -> Payment: REJECTED, Booking: REJECTED (Reason recorded)
```

## 6. Storage & Notification Abstractions

- **Storage**: `IStorageService` implemented by `LocalStorageService` (development) and `S3StorageService` (production).
- **Notifications**: `INotificationService` and `ISmsProvider` interface prepared for Iranian SMS gateways (Kavenegar, FarazSMS, etc.).
